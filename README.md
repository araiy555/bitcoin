# jsboard — 仮想通貨のマーケットメイク板

Binance の板を取り込み、マーケットメイカーを走らせ、ターミナルに板を描く。
マッチングエンジン・MM エンジン・可視化の3層すべてを自前で実装している。

```
                    ┌──────────────┐
   Binance WS ─────▶│  Feed        │  depth diff + aggTrade を正規化
   合成 / リプレイ ─▶│  (adapter)   │  ticks / lots に変換
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
                    │  MarketView  │  板 + 歩み値 + σ + フロー不均衡
                    └──────┬───────┘
                           ▼
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌───────────┐     ┌───────────┐      ┌───────────┐
  │FairValue  │────▶│  Quoter   │◀─────│   Risk    │
  │microprice │     │ skew/幅   │      │ 限度/停止 │
  └───────────┘     └─────┬─────┘      └───────────┘
                          ▼
                   ┌─────────────┐     ┌───────────┐
                   │ PaperVenue  │────▶│ Position  │
                   │ キュー位置  │     │ 平均原価  │
                   └─────────────┘     └───────────┘
                          ▼
                   ┌─────────────┐
                   │   Board     │  rich による板表示
                   └─────────────┘
```

実装の全仕様は [SPEC.md](SPEC.md) にある。

## 実行

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]"

jsboard triage --maker-bps 10      # 全銘柄を10秒で落とす（必ず最初にこれ）
jsboard scan --maker-bps 10        # 手数料を超える銘柄があるか探す
jsboard sim                        # 合成市場 + ライブ板（ネットワーク不要）
jsboard backtest --seed 7          # ヘッドレス実行、P&L サマリのみ
jsboard live --symbol BTCUSDT      # Binance の実板、約定はペーパー
jsboard record --out cap.jsonl     # ライブセッションを記録
jsboard replay cap.jsonl --speed 4 # 記録を再生
```

BTC の現物と無期限先物を、起きた順のまま1本のファイルに記録する：

```bash
jsboard capture --symbol BTCUSDT --duration 60 --out btc.jsonl
```

最初は必ず短く走らせて、`spot` と `perp` の両方が届いているか確認してください。
片方が 0 件なら接続の問題で、長く回しても中身は増えません。

## 最初に確認すべきこと

**この戦略は、手数料がゼロ以下でなければ成立しません。** 建値を出して稼げるのは
1往復あたり最大でスプレッド1回分、対して手数料は売り買いの両方にかかるので、

```
spread_bps  >  2 × maker_fee_bps
```

を満たさない限り、1回売買するごとに必ず損をします。BTCUSDT でこれは
**0.003 対 20** であり、成立しません。約6,400倍足りない計算です。

`jsboard scan` は同じ判定を全銘柄に対して行います。ただし
**手数料を超えることは必要条件であって、十分条件からは程遠い**ので、
残った銘柄をさらに2つの罠でふるいにかけます。

| 判定 | 意味 |
|---|---|
| 行列が長い | 自分の前に並ぶ金額が大きすぎて順番が回らない |
| 板が薄い | 自分の注文が板の大半を占める。並ぶ相手がおらず、抜けられない |

実測では、10bps で手数料を超えた12銘柄のうち8件がこのどちらかで脱落しました。

さらに、**薄い板は1回の観測では判定できません。** 実際に数分違いで
SHIBUSDT の板が 20,723 → 4,841 USDT（4倍以上）動き、判定が反転しました。
既定では板を5回観測して中央値で判定し、「板のぶれ」列に観測中の変動幅を出します。
ここが 3x を超える銘柄の数字は、そのまま信じないでください。

## それでも1回のスキャンでは足りない

10秒の観測窓でノイズは消えますが、**答えそのものが持続しません。**
30分空けて2回スキャンした実測では、手数料を超えた12銘柄のうち重複は6件だけ、
「注文が置ける」4銘柄のうち次も残ったのは1件でした。BONKUSDT の板は
15,793 → 2,354 USDT（0.15倍）、MIRAUSDT は 18,142 → 1,688（0.09倍）に落ち、
どちらも判定が反転しています。

```bash
jsboard watch --maker-bps 10 --rounds 12 --every 300   # 5分×12回 = 1時間
```

`watch` はスキャンを繰り返し、**全ラウンドを分母として**各銘柄の持続率を出します。
途中から現れた銘柄が有利にならないよう、登場した回だけで割ることはしません
（「そもそも条件から外れて消えていた」ことが、まさに測りたい不安定さなので）。

建値を出し続ける戦略の対象になるのは、持続率が高い銘柄だけです。
1回のスキャンで「可」と出た数件は、その瞬間の話でしかありません。

## 実測結果（1時間 × 2条件）

同じ1時間の watch を、手数料 10bps と 0bps で回した結果。

| | 10 bps | 0 bps |
|---|---|---|
| 一度でも手数料を超えた | 24件 | 131件 |
| **75%以上の回で置けた** | **0件** | **13件** |

**壁は手数料でした。** そして残る銘柄の性質が入れ替わります。10bps で
かろうじて条件を満たすのは板が100〜900倍ぶれる薄い銘柄ばかりで、
利ざや最大の LAZIOUSDT（+37.72 bps）は12回中1度も置けていません。
0bps では ASTER(ぶれ2.0x)・ENA(2.1x)・SOL(1.8x) と、板の安定した銘柄が並びます。

そこで watch は **「上限手数料」= スプレッド ÷ 2** を出します。
これを下回る手数料が取れれば成立する、という水準です。

```
ASTERUSDT   持続率100%   上限 8.32 bps   板 24,118   ぶれ 2.0x
WLFIUSDT    持続率 92%   上限 9.13 bps   板 11,344   ぶれ 3.8x
BONKUSDT    持続率 75%   上限17.95 bps   板  9,963   ぶれ 6.6x
SOLUSDT     持続率100%   上限 0.69 bps   板 19,648   ぶれ 1.8x
BTCUSDT     持続率 17%   上限 0.00 bps   板125,799   ぶれ52.1x
```

BTC・ETH・XRP・BNB は板こそ厚く安定していますが、スプレッドが1tick しかなく
**上限手数料がほぼゼロ**。0bps でなければ成立しません。

一方 ASTER・WLFI は上限が 8〜9 bps あり、VIP2 相当の手数料まで耐えます。
**手数料は交渉やVIP昇格で動かせますが、スプレッドは動かせません。**
だから「今の手数料で成立するか」より「どの手数料が必要か」を出すほうが役に立ちます。

実注文を出す経路は存在しない。`live` は実データを読むだけで、
API キーを受け取る箇所も取引所への発注パスもコード上に無い。

`sim` / `backtest` / `replay` はネットワーク不要。
`live` / `record` は `api.binance.com` と `stream.binance.com` への到達性が要る。
到達できない場合は例外で落ちるのではなく、exchangeInfo は内蔵スペックに
フォールバックし、WS は指数バックオフで再接続を試み、その間リスクゲートが
`PULL: feed is disconnected` を返して建値を出さない。

## 各層について

### マッチングエンジン（`core/book.py`）

価格-時間優先の板。片側ごとに `SortedDict[price → PriceLevel]` を持ち、
ベスト気配は `peekitem` で O(1)。レベル内は `deque` で到着順。

キャンセルは中間要素を抜かず、注文を死んだ状態にしてレベル合計から差し引く。
死んだ注文はキュー先頭に来た時点で捨てる。キャンセルが O(1) になる代わりに、
浮上するまでオブジェクトが残る。この形の板では標準的な取引。

価格は **tick 単位の整数**、数量は **lot 単位の整数** で保持する。
板に浮動小数点が入らないので、価格レベルの比較とハッシュが厳密に一致する。
人間向けの単位への変換は `Instrument` だけが行う。

GTC / IOC / FOK / POST_ONLY、成行、部分約定、自己約定防止（STP）に対応。

### Binance 同期（`feed/binance.py`）

このファイルの主眼はスナップショットと差分の継ぎ目。Binance は板の差分を
連続配信する一方でベース画像は REST で配るため、取りこぼしも二重適用もなく
繋ぐ必要がある。公式手順どおり：

1. 差分ストリームを開いてバッファリング開始
2. REST スナップショットを取得し `lastUpdateId` を記録
3. `u <= lastUpdateId` のイベントを破棄
4. 最初に適用するイベントは `U <= lastUpdateId+1 <= u` を満たすこと
5. 以降すべて `U == 前回の u + 1`。ギャップ検出時は再同期

4 と 5 を省いても例外は出ない。静かに数レベルずれた板が延々と出来上がる。
この失敗モードこそ守る価値があるので、結合条件とギャップ条件は
`tests/test_binance_sync.py` で直接テストしている。

### フェアバリューとクォート（`mm/`）

マーケットメイカーにとって仲値は誤ったアンカーで、板のどちら側が厚いかを
無視する。仲値の周りに対称に置くマーケットメイカーは逆選択される。
起点は **microprice**（サイズ加重の仲値。薄い側に寄る）とし、
板の不均衡と直近の約定フローで補正する。

価格は Avellaneda–Stoikov の2つの発想に従う。

- **リザベーション価格** — 在庫を持つと売りたくなる。クォート対を在庫と逆に
  ずらすことで、スプレッドを払って手仕舞う代わりに市場が在庫を戻してくれる
- **ハーフスプレッド** — ボラが高いほど広く、板が薄く回復が遅いほど広く

ただし**パラメータ化は論文どおりではない**。原論文の γ は次元を持ち、
`γ·σ²·T` が価格になるのは γ が 1/(価格·数量) の単位を担っているから。
これを素朴に tick 空間へ移すと全パラメータが銘柄依存になる。
tick が $0.01 の銘柄で妥当なスプレッドを出す γ が、別の銘柄では5桁になる。

そこで同じ構造を、銘柄が変わっても意味が保たれる単位で表す：

```
skew_ticks  = (inventory_skew_ticks + gamma·σ_ticks) · q_norm
half_spread = base + vol_multiplier·σ_ticks + liquidity_premium/κ
```

`q_norm` は建玉上限に対する比率なので [-1, 1] に収まり、σ は tick 単位なので
両項とも tick。γ・`vol_multiplier`・κ は無次元で、どの銘柄でも同じ意味を持つ。

**手数料はクォート幅に効く。** メイカー手数料 `f` bps を払う以上、
片側あたり最低 `f` bps は稼がねば round trip が成立しない。
`min_edge_bps` がハーフスプレッドの下限として効き、CLI では
`--maker-bps` から自動で設定される。これが無いと、手数料より1桁狭い
スプレッドで喜んで建値を出し、予測精度に関係なく必ず負ける。

### ペーパー約定（`sim/paper.py`）

面白いのはキュー位置。指値は自分の価格で約定が起きたから約定するのではなく、
**先に並んでいた全員を市場が食い破ったから**約定する。
よって各注文は、置いた時点で前方にあったサイズを記憶し、
歩み値がその滞留分を消化してから初めて自分に届く。

モデル化しているもの：

- 板の見えている厚みから決まる FIFO キュー位置
- 価格改善 — スプレッド内側に置けば最前列
- 部分約定と、レベル枯渇のより良い価格への波及
- 発注レイテンシ（決めた瞬間に板に乗るわけではない）

**していないもの**（結果が甘くなる方向）：

- マーケットインパクト
- 自分の前にある見えない板（アイスバーグ等）
- 到着後に追い抜いてくる、より速い参加者
- **ギャップスルー** — 歩み値を挟まず板が指値を飛び越えた場合、
  現実なら通り過ぎざまに誰かに取られているが、ここでは約定しない。
  これがモデル最大の楽観であり、マーケットメイカーが最も恐れる逆選択を
  過小評価する。**P&L は推定値ではなく上限として読むこと。**

`cancel_ahead_ratio` は最大の不確実性に対する唯一の正直なつまみ。
歩み値なしに自分のレベルの厚みが減ったとき、それが自分の前で消えたのか
後ろで消えたのかは観測できない。0.0 は悲観（全部後ろ）、1.0 は楽観（全部前）。

### リスク（`mm/risk.py`）

全クォートサイクルは発注前にリスクゲートを通る。ゲートは
両建て継続 / 片側のみ / 全取消 / 停止 を返す。停止は**ラッチする**。
ドローダウン超過は次のティックで数字が改善しても解除されず、
明示的にリセットするまで固定される。

ステールネス判定は見た目より重要。10秒前に更新が止まった板に建値を出すのは、
下落相場で唯一の買い手になる典型的な経路。

## 合成市場について

`SyntheticFeed` はドリフトなしのランダムウォーク。
**したがってマーケットメイカーは手数料前でほぼフラットになるのが正しい。**
ここで安定して利益が出るなら、それは戦略が良いのではなく
シミュレータが壊れている。

デフォルト値は個別に現実的というより**相互に整合**するよう選んである。
100ms あたり 0.1bps は日次約1%に相当し、8 tick のスプレッドと 2万 lot の
レベルと組み合わせると、内側に置ける程度に広く、キュー位置が意味を持つ程度に
深い板になる。

実際に手数料 1bps を指定すると：

```
$ jsboard backtest --maker-bps 1.0
  fills : 0    total P&L : +0.00 USDT
```

ハーフスプレッド下限が 640 tick（$6.40）まで広がり、
合成市場の $0.08 スプレッドでは一切約定しない。
これはバグではなく正しい結論で、$0.08 のスプレッドに対して
1bps のメイカー手数料を払う BTCUSDT 現物のマーケットメイクは成立しない。

## 現状の制約

- 発注はペーパーのみ。実発注パスは無い
- ギャップスルー約定を模擬していない（上記）
- MM パイプラインは単一銘柄。クロス銘柄のヘッジや相関リスクは扱わない
- Binance のみ。他取引所は `Feed` を実装すれば差し替え可能
- σ は 1 更新あたりの実現ボラで、日中の季節性は持たない
- **`capture` は実データに一度も当てていない**（開発環境から
  binance.com への通信が塞がれているため）。ロジックはフェイクソケットで
  検証済みだが、実際の fapi / fstream での挙動は未確認

## 結論 — 壁は手数料ではなく、その手前にあった

この調査は終了した。**すべて実データによる測定で、意見ではない。**

| 調べたこと | 結果 |
|---|---|
| マーケットメイク | 実手数料で置ける銘柄 **1件**（手数料0なら10件） |
| 数秒の方向予測 | 10秒の値動き 0.95 bps < 往復コスト 9.03 bps。**算数として不可能** |
| 1時間の方向予測 | 必要 60.8%、実測 **47.6%**。学習では57.8%だった |
| 実際に建値を出した（WIFUSDT 先物） | **18通りすべて、手数料を引く前から赤字** |

### 最後の測定 — 手数料の話ではなかった

3回とも「手数料が壁だ」と結論していたが、実際に建値を出して約定を数えたら
壁はもっと手前にあった。WIFUSDT 先物を1時間録画し、同じ録画に対して
18通りの設定を再生した結果：

| | 取り bps（手数料前） | 約定 |
|---|---|---|
| 最良 | **−0.15** | 222 |
| 最悪 | **−5.82** | 118 |

**18通りすべてで、手数料を1銭も引く前からマイナス。** 手数料ゼロでも
黒字にならない。VIP昇格でも口座移転でも動かない種類の負けである。

原因は2つ、どちらも測定で切り分けた。

**1. tick が粗すぎて逃げ場がない。** WIF は 1tick = 7.37 bps。スプレッドは
ほぼ常に1tick なので、選べるのは「最良気配に貼り付く」か「約定しない」かの
二択しかない。実測でも1tick 離した瞬間、1時間の約定が 200件 → **2件**に落ちた。
在庫に応じて建値をずらすという動作が、板の構造上とれない。

**2. 負けているのは約定の瞬間ではなく、その後の在庫。**
10秒 mark-out はほぼ中立（−0.24 bps）なのに取りは −5.77 bps。
逆選択で抜かれているのではなく、貼り付き続けて溜まった建玉が後から不利に動く。

**銘柄選定の基準がここで変わった。** スプレッドが何 bps あるかではなく、
**何 tick 分あるか**。1tick しかない銘柄は、bps がいくら広く見えても
マーケットメイクの余地がない。`scan` はこれを見ていない。

### 最終判定 — エッジは実在した。ヘッジ代がそれを上回った

損益を恒等式で分解したところ（`Total = スプレッド取り + 在庫 − 手数料`）、
100ms 更新で板に貼り付いたとき **スプレッド取り +7.5 bps** が出た。
WIF の半スプレッド 3.7 bps の往復ぶんに一致する、理論上の満額である。
**マーケットメイクのエッジそのものは実在した。**

それを在庫が食っていた。在庫を保有時間で割ると、損失が二極化しているのが見えた。

| 保有時間 | 在庫損益 (bps) | 届くか |
|---|---|---|
| 0-100ms | −2.3 〜 −3.5 | **届かない**（板の更新間隔そのもの） |
| 100ms-1s | **±0.04** | — |
| 1-10s | −1.3 〜 +0.1 | 届く |
| 10s+ | **−3.7 〜 −8.3** | 届く |

100ms〜1秒の損失がゼロ。ミリ秒級のヘッジは要らず、数秒で在庫を落とせば
最大項が消える、という形である。そこで最終テストを1本だけ回した
（`jsboard hedge`）— WIF spot でメイクし、約定した瞬間に WIF perp を成行でヘッジ。

```
maker   約定  make.spread  make.在庫  hedge.cross  hedge.在庫  手数料   Net bps
0       73    +7.49        -2.44      -9.21        -3.40       -12.45   -20.01
1       73    +7.49        -2.44      -9.21        -3.40       -14.94   -22.50
2       73    +7.49        -2.44      -9.21        -3.40       -17.43   -24.99
```

**ヘッジは効いた。** 在庫損は −7〜−11 bps から **−2.44** に落ちている。
そして効いた代償が、

- 板を叩くコスト **−9.21**（1tick = 7.37 bps の板を往復で2回以上クロスする）
- テイカー手数料 **−12.45**
- 両脚のベーシス **−3.40**

合わせて **−25 bps**。救った在庫は 5〜9 bps。**治療費が病気の3倍だった。**

手数料ゼロでも Net −20.01。VIP 階層でも口座移転でも動かない。ここで終了。

### この調査の本当の失敗は、順番だった

WIF の結論は、3つの数字から5分で出せた。

```
1tick   = 0.0001 / 0.1356  = 7.37 bps
spread  = 1 tick           = 7.37 bps
maker   = 10 bps           → 往復 20 bps
```

板を全部取っても 7.37 で、往復コストが 20。**バックテスト以前に終わっている。**
実際には数日かけて同じ場所に着いた。戦略の問題ではなく、検証順序の問題である。

そこで `jsboard triage` を入れた。手数料・tick 幅・スプレッドだけで全銘柄を
一次審査し、`スプレッド bps − 2 × メイカー bps ≤ 0` を即座に落とす。
加えて **スプレッドが 2 tick 未満**も落とす — 1tick しかない板では、
最良気配に貼り付くか約定しないかの二択しかなく、在庫に応じて建値を
ずらす動作が物理的に取れないため。

```
数百銘柄を一次審査 (triage, 10秒)
  ↓ 上位だけ
capture で録画 (1時間放置)
  ↓
sweep で設定を掃引 (数分)
  ↓ 手数料前がプラスのものだけ
hedge で全コスト込み判定 (数分)
  ↓
別期間で out-of-sample → ペーパー → 少額実弾
```

**「勝てるまで直す」のではなく「落とすために測る」。** 100個試して98個捨てて
2個残ればいい。1銘柄に数日かけて最後に無理と分かる形を、二度と作らない。

### 次の検証 — USUSDT（判定条件は測定前に固定）

WIF の敗因は tick の粗さだった、というのが今の仮説である。ならば
**tick が細かいほどクォートを細かく動かせ、逆選択と在庫制御が改善するはず**で、
それが出なければ「tick の細かさが MM 成立性を救う」という仮説自体が弱い。

一次審査で全軸最良だった USUSDT で確かめる。WIF との対比：

| | WIF | USUSDT |
|---|---|---|
| 1tick | 7.37 bps | **0.45 bps**（16分の1） |
| spread | 1 tick | **21 tick** |
| 24h約定 | — | 193万件 |

```
jsboard capture --symbol USUSDT --duration 3600 --out us.jsonl
jsboard sweep us.jsonl --source perp --maker-bps 2 \
  --distances 0 --axis requote-ms=100,250,1000 --plain
```

見るのは 100ms 行の2列だけ。**測定前に決めた判定：**

| 条件 | 結論 |
|---|---|
| 手数料前 bps ≤ 0 | **USUSDT 終了。**ヘッジ以前の問題 |
| 許容料率 ≤ 2 bps | **2 bps 口座でも終了。**手数料で届かない |
| 手数料前 > 0 かつ 許容料率 > 2 bps | 在庫・ヘッジ検証へ進む |

参考として WIF の同じ2列は、100ms 最良行で
**手数料前 −0.36 bps / 許容料率 −0.18 bps** だった。

なお余裕 bps（一次審査の列）は実行ごとに大きく振れる — USUSDT は3回の実行で
+15.22 / +2.46 / +5.53 だった。銘柄選択はこの列ではなく、exchangeInfo 由来で
安定している **tick 幅・スプレッドの tick 数・約定件数**で行っている。

### 結果 — 仮説は否定された。tick の細かさは救わない

| | WIF | USUSDT | |
|---|---|---|---|
| 1tick | 7.37 bps | **0.45 bps** | 16分の1 |
| spread | 1 tick | **21 tick** | |
| 1時間の約定 | 177 | **39,434** | 223倍 |
| スプレッド取り | +6.75 | **+1.51** | ↓ |
| 在庫 | −7.11 | **−32.53** | ↓↓ |
| 逆選択 100ms | −2.26 | **−12.48** | **5.5倍悪い** |
| **手数料前** | −0.36 | **−31.02** | |
| **許容料率** | −0.18 | **−15.51** | |

事前に決めた条件（手数料前 ≤ 0）で **USUSDT 終了**。しかも僅差ではない。

重要なのは**仮説が逆方向に外れた**ことである。tick を16分の1にすれば
逆選択と在庫制御が改善するはずだったが、逆選択は **5.5倍悪化**した。
約定数が223倍なので、統計としては WIF の測定より遥かに強い。
**「tick の細かさが MM 成立性を救う」は捨てる。**

理由はおそらく単純で、tick ではなく**価格が動く速さ**である。USUSDT は
スプレッドが 9.53 bps しかないのに、約定から 100ms で mid が **12.48 bps**
逆行する。**スプレッド1本ぶんより速く価格が動く板**では、100ms 間隔で
更新する限り常にクォートが陳腐化しており、tick がどれだけ細かくても関係ない。
実際、板に貼り付いて 21 tick のスプレッドを持つ板で、取れたのは 1.51 bps
だけだった。

### 一次審査が見ていないもの

この失敗は `triage` を通過している。手数料・tick 幅・スプレッドの tick 数は
すべて合格で、それでも成立しなかった。**審査は静的な板の形しか見ておらず、
価格が動く速さを見ていない。** 判定に効くのはおそらく

    100ms の逆選択 ÷ スプレッド

で、これが 1 を超える板は、100ms で反応する限りどうやっても負ける
（USUSDT は 12.48 / 9.53 = 1.31、WIF は 2.26 / 7.37 = 0.31）。
ただしこれは板データが要るので、REST 2発の一次審査には入らない。

### 二次審査 — 100ms で生き残れる板が市場に存在するか

1銘柄1時間の録画を候補の数だけ繰り返すのは高すぎる。`jsboard probe` は
triage を通った銘柄を**まとめて5分間**観測し、この比率だけを出す。

**ペーパー MM は走らせない。** 公開約定はすべて「列の先頭にいたら約定していた
もの」なので、歩み値だけでメイカー側の逆選択が測れる — 成行買いはメイカーの
売り、成行売りはメイカーの買い。符号を仕掛け側から取ることで、**約定モデルが
測定から完全に外れる**（キュー位置の仮定も、突き抜け約定の取りこぼしもない）。
サンプル数は市場が実際に約定した回数そのものになる。

```
jsboard probe --duration 300          # triage の候補を自動で引き継ぐ
jsboard probe --symbols A,B,C --duration 300
```

| MO/spread | 判定 |
|---|---|
| < 0.5 | 研究候補 |
| 0.5 〜 1.0 | 見込み薄 |
| ≥ 1.0 | 不可（スプレッドが払う以上に価格が動く） |

0.5 という線は実証値ではない。1 のすぐ下では手数料・在庫・約定モデルの
楽観に充てる余白が残らないので半分に置いてある。**通っても最終判断は
Net PnL で行う。**

**測定前に固定した終了条件：**

| 結果 | 結論 |
|---|---|
| 研究候補ゼロ | **100ms・板貼りつき MM の探索を終了** |
| 研究候補あり | その銘柄だけ 1時間 capture → sweep → hedge を**一度だけ** |

測定できた銘柄がゼロだった場合は判定にならない（何も棄却していない）ので、
終了条件は発動しない。

3つ目が最も示唆的だった。学習期間で最良だった信号が、検証期間では
コイン投げ以下に落ちた（57.8% → 47.6%）。**時系列分割を守らなければ
「57.8%の的中率」を成果として報告していた。**

詳細と数字は [SPEC.md](SPEC.md) §15。

### 検証していないこと

「エッジは存在しない」の証明ではない。試したのは単一特徴・符号のみの
12信号、14日ぶん、単一製品。組み合わせも機械学習もクロス製品特徴も
未実施。そして閉じたのは**固定ホライズン・全時点・両側テイカー**という設計で
あって、「秒単位に優位性が無い」ではない。必要的中率の式は勝ち幅と負け幅が
等しい前提の簡略形で、利確・損切りを置けば話が変わる。イベント条件付きの
条件付き平均変動も、無条件平均の 0.95 bps より大きくなり得る。

マーケットメイクの側も同じで、閉じたのは **WIFUSDT 1銘柄・1時間・18設定**で
あって、「マーケットメイクが成立しない」ではない。tick の粗い銘柄を選んだのは
こちらの判断ミスであり、スプレッドが数 tick ある銘柄では別の結果になり得る。
ただしその場合も、`live` の損益は上限値として読むこと — ペーパー約定は
板を突き抜ける約定（gap-through）を数えておらず、それは必ずこちらが損をする側の
約定だからである。**上限値で赤字なら、実弾は確実に赤字。**

## 使える道具として残るもの

上のスキャン／マーケットメイクが測っているのは「**マーケットメイクの適性**」で、
「**予測できるか**」ではありません。BTC が落ちたのは板が読めなかったからではなく、
最良気配1段でのメイク適性が低いからです。別の問いには別の道具が要ります。

```bash
jsboard horizon --symbol BTCUSDT --days 7    # 値動きが手数料を超えるか
jsboard predict --symbol BTCUSDT --days 14   # 信号が必要精度に届くか
jsboard capture --symbol BTCUSDT             # 現物+先物を1本の時系列に記録
jsboard scan --maker-bps 10                  # 全銘柄のメイク適性
```

`horizon` と `predict` は**別の銘柄・別の手数料でそのまま使える**。
別の市場を検討するときは、作り込む前にこの2つを通すのが安い。


## 選択的MM — 危険な側を出さない

常時両側に貼る戦略は、USUSDTで注文遅延を20msから2msへ縮めても
手数料前 −12.49bpsだった。原因は処理速度ではなく、不利な方向へ動く直前の
約定だけを受けやすい逆選択である。

選択的MMは、注文を出す時点ですでに見えている3信号だけを使う。

- 直近の成行買い・成行売りの偏り
- 複数段の買い板・売り板の不均衡
- micropriceの仲値からのずれ

scoreが正なら上昇圧力なので売り注文を止め、負なら下落圧力なので買い注文を
止める。絶対値が`--toxicity-pull-threshold`以上なら両側を取り消す。
未来価格や約定後mark-outは判定に使わない。

まず同じ録画で閾値だけを比較する。

```bash
jsboard sweep us.jsonl --source perp \
  --requotes 100 --latencies 2 \
  --toxicity-thresholds 0,0.2,0.4,0.6,0.8 --plain
```

`0`は従来戦略そのものなので対照群になる。見る列は手数料前・約定・
毒性片側%・毒性全取消%。閾値を上げるほど手数料前が一貫して改善しなければ、
この3信号には危険約定を避ける情報がない。改善しても、この録画で閾値を選んだ
時点で学習内なので、設定を固定して別時間の録画で再検証するまで採用しない。


## 相対価値MM — ヘッジできる価格から先に注文を作る

`hedge` は単体市場で出した注文を約定後にヘッジする診断だった。`pair` は順序が
違う。現物でメイクするなら先物の実際の板をFair Valueにし、提案した各注文を
同数量の即時ヘッジと組み合わせる。次をすべて引いても指定した余白が残る注文だけ
ペーパー板へ出す。

- maker手数料
- hedge側のtaker手数料
- 注文数量で実際に板を歩いた価格
- 古いヘッジ板の拒否
- 見えている板で全数量をヘッジできない注文の拒否

まず現物と先物を同じ時系列へ記録し、その録画で判定する。

```bash
.venv/bin/jsboard capture --symbol BTCUSDT --duration 3600 --out btc-pair.jsonl

.venv/bin/jsboard pair btc-pair.jsonl \
  --maker-source spot \
  --hedge-source perp \
  --maker-fees 0,1,2 \
  --taker-bps 4 \
  --pair-edge-bps 1 \
  --requote-ms 100 \
  --latency-ms 2 \
  --hedge-latency-ms 2 \
  --plain
```

`候補%`は全執行コスト後に注文を出せた割合、`最良edge`は発注前に見えていた最大の
執行コスト後余白。候補が0なら損失0のまま銘柄・期間を棄却する。候補があっても
約定0なら価格差はキューを突破するほど持続していない。`Net bps`がプラスになって
初めて、設定を固定した別時間の録画へ進む。

このコマンドも実注文は送らない。ペーパー約定はgap-throughを数えないため、
結果は従来と同じく上限値として読む。`--hedge-latency-ms`はmaker約定から
hedge注文到達まで待ち、その時点で見えている板を歩く。Fundingの実決済と
借入金利はまだ会計に含めないため、ポジションをFunding時刻またぎで持つ検証には
この版だけを使わない。
