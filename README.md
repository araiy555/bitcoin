# jsboard — 仮想通貨のマーケットメイク板

Binance の板を取り込み、マーケットメイカーを走らせ、ターミナルに板を描く。
マッチングエンジン・MM エンジン・可視化の3層すべてを自前で実装している。

```
                    ┌──────────────┐
   Binance WS ─────▶│  Feed        │  depth diff + aggTrade を正規化
   合成 / リプレイ ─▶│  (adapter)   │  ticks / lots に変換
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
                    │  MarketView  │  板 + 歩み値 + σ + フロー不均衡
                    └──────┬───────┘
                           ▼
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌───────────┐     ┌───────────┐      ┌───────────┐
  │FairValue  │────▶│  Quoter   │◀─────│   Risk    │
  │microprice │     │ skew/幅   │      │ 限度/停止 │
  └───────────┘     └─────┬─────┘      └───────────┘
                          ▼
                   ┌─────────────┐     ┌───────────┐
                   │ PaperVenue  │────▶│ Position  │
                   │ キュー位置  │     │ 平均原価  │
                   └─────────────┘     └───────────┘
                          ▼
                   ┌─────────────┐
                   │   Board     │  rich による板表示
                   └─────────────┘
```

実装の全仕様は [SPEC.md](SPEC.md) にある。

## 実行

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]"

jsboard scan --maker-bps 10        # 手数料を超える銘柄があるか探す（最初にこれ）
jsboard sim                        # 合成市場 + ライブ板（ネットワーク不要）
jsboard backtest --seed 7          # ヘッドレス実行、P&L サマリのみ
jsboard live --symbol BTCUSDT      # Binance の実板、約定はペーパー
jsboard record --out cap.jsonl     # ライブセッションを記録
jsboard replay cap.jsonl --speed 4 # 記録を再生
```

BTC の現物と無期限先物を、起きた順のまま1本のファイルに記録する：

```bash
jsboard capture --symbol BTCUSDT --duration 60 --out btc.jsonl
```

最初は必ず短く走らせて、`spot` と `perp` の両方が届いているか確認してください。
片方が 0 件なら接続の問題で、長く回しても中身は増えません。

## 最初に確認すべきこと

**この戦略は、手数料がゼロ以下でなければ成立しません。** 建値を出して稼げるのは
1往復あたり最大でスプレッド1回分、対して手数料は売り買いの両方にかかるので、

```
spread_bps  >  2 × maker_fee_bps
```

を満たさない限り、1回売買するごとに必ず損をします。BTCUSDT でこれは
**0.003 対 20** であり、成立しません。約6,400倍足りない計算です。

`jsboard scan` は同じ判定を全銘柄に対して行います。ただし
**手数料を超えることは必要条件であって、十分条件からは程遠い**ので、
残った銘柄をさらに2つの罠でふるいにかけます。

| 判定 | 意味 |
|---|---|
| 行列が長い | 自分の前に並ぶ金額が大きすぎて順番が回らない |
| 板が薄い | 自分の注文が板の大半を占める。並ぶ相手がおらず、抜けられない |

実測では、10bps で手数料を超えた12銘柄のうち8件がこのどちらかで脱落しました。

さらに、**薄い板は1回の観測では判定できません。** 実際に数分違いで
SHIBUSDT の板が 20,723 → 4,841 USDT（4倍以上）動き、判定が反転しました。
既定では板を5回観測して中央値で判定し、「板のぶれ」列に観測中の変動幅を出します。
ここが 3x を超える銘柄の数字は、そのまま信じないでください。

## それでも1回のスキャンでは足りない

10秒の観測窓でノイズは消えますが、**答えそのものが持続しません。**
30分空けて2回スキャンした実測では、手数料を超えた12銘柄のうち重複は6件だけ、
「注文が置ける」4銘柄のうち次も残ったのは1件でした。BONKUSDT の板は
15,793 → 2,354 USDT（0.15倍）、MIRAUSDT は 18,142 → 1,688（0.09倍）に落ち、
どちらも判定が反転しています。

```bash
jsboard watch --maker-bps 10 --rounds 12 --every 300   # 5分×12回 = 1時間
```

`watch` はスキャンを繰り返し、**全ラウンドを分母として**各銘柄の持続率を出します。
途中から現れた銘柄が有利にならないよう、登場した回だけで割ることはしません
（「そもそも条件から外れて消えていた」ことが、まさに測りたい不安定さなので）。

建値を出し続ける戦略の対象になるのは、持続率が高い銘柄だけです。
1回のスキャンで「可」と出た数件は、その瞬間の話でしかありません。

## 実測結果（1時間 × 2条件）

同じ1時間の watch を、手数料 10bps と 0bps で回した結果。

| | 10 bps | 0 bps |
|---|---|---|
| 一度でも手数料を超えた | 24件 | 131件 |
| **75%以上の回で置けた** | **0件** | **13件** |

**壁は手数料でした。** そして残る銘柄の性質が入れ替わります。10bps で
かろうじて条件を満たすのは板が100〜900倍ぶれる薄い銘柄ばかりで、
利ざや最大の LAZIOUSDT（+37.72 bps）は12回中1度も置けていません。
0bps では ASTER(ぶれ2.0x)・ENA(2.1x)・SOL(1.8x) と、板の安定した銘柄が並びます。

そこで watch は **「上限手数料」= スプレッド ÷ 2** を出します。
これを下回る手数料が取れれば成立する、という水準です。

```
ASTERUSDT   持続率100%   上限 8.32 bps   板 24,118   ぶれ 2.0x
WLFIUSDT    持続率 92%   上限 9.13 bps   板 11,344   ぶれ 3.8x
BONKUSDT    持続率 75%   上限17.95 bps   板  9,963   ぶれ 6.6x
SOLUSDT     持続率100%   上限 0.69 bps   板 19,648   ぶれ 1.8x
BTCUSDT     持続率 17%   上限 0.00 bps   板125,799   ぶれ52.1x
```

BTC・ETH・XRP・BNB は板こそ厚く安定していますが、スプレッドが1tick しかなく
**上限手数料がほぼゼロ**。0bps でなければ成立しません。

一方 ASTER・WLFI は上限が 8〜9 bps あり、VIP2 相当の手数料まで耐えます。
**手数料は交渉やVIP昇格で動かせますが、スプレッドは動かせません。**
だから「今の手数料で成立するか」より「どの手数料が必要か」を出すほうが役に立ちます。

実注文を出す経路は存在しない。`live` は実データを読むだけで、
API キーを受け取る箇所も取引所への発注パスもコード上に無い。

`sim` / `backtest` / `replay` はネットワーク不要。
`live` / `record` は `api.binance.com` と `stream.binance.com` への到達性が要る。
到達できない場合は例外で落ちるのではなく、exchangeInfo は内蔵スペックに
フォールバックし、WS は指数バックオフで再接続を試み、その間リスクゲートが
`PULL: feed is disconnected` を返して建値を出さない。

## 各層について

### マッチングエンジン（`core/book.py`）

価格-時間優先の板。片側ごとに `SortedDict[price → PriceLevel]` を持ち、
ベスト気配は `peekitem` で O(1)。レベル内は `deque` で到着順。

キャンセルは中間要素を抜かず、注文を死んだ状態にしてレベル合計から差し引く。
死んだ注文はキュー先頭に来た時点で捨てる。キャンセルが O(1) になる代わりに、
浮上するまでオブジェクトが残る。この形の板では標準的な取引。

価格は **tick 単位の整数**、数量は **lot 単位の整数** で保持する。
板に浮動小数点が入らないので、価格レベルの比較とハッシュが厳密に一致する。
人間向けの単位への変換は `Instrument` だけが行う。

GTC / IOC / FOK / POST_ONLY、成行、部分約定、自己約定防止（STP）に対応。

### Binance 同期（`feed/binance.py`）

このファイルの主眼はスナップショットと差分の継ぎ目。Binance は板の差分を
連続配信する一方でベース画像は REST で配るため、取りこぼしも二重適用もなく
繋ぐ必要がある。公式手順どおり：

1. 差分ストリームを開いてバッファリング開始
2. REST スナップショットを取得し `lastUpdateId` を記録
3. `u <= lastUpdateId` のイベントを破棄
4. 最初に適用するイベントは `U <= lastUpdateId+1 <= u` を満たすこと
5. 以降すべて `U == 前回の u + 1`。ギャップ検出時は再同期

4 と 5 を省いても例外は出ない。静かに数レベルずれた板が延々と出来上がる。
この失敗モードこそ守る価値があるので、結合条件とギャップ条件は
`tests/test_binance_sync.py` で直接テストしている。

### フェアバリューとクォート（`mm/`）

マーケットメイカーにとって仲値は誤ったアンカーで、板のどちら側が厚いかを
無視する。仲値の周りに対称に置くマーケットメイカーは逆選択される。
起点は **microprice**（サイズ加重の仲値。薄い側に寄る）とし、
板の不均衡と直近の約定フローで補正する。

価格は Avellaneda–Stoikov の2つの発想に従う。

- **リザベーション価格** — 在庫を持つと売りたくなる。クォート対を在庫と逆に
  ずらすことで、スプレッドを払って手仕舞う代わりに市場が在庫を戻してくれる
- **ハーフスプレッド** — ボラが高いほど広く、板が薄く回復が遅いほど広く

ただし**パラメータ化は論文どおりではない**。原論文の γ は次元を持ち、
`γ·σ²·T` が価格になるのは γ が 1/(価格·数量) の単位を担っているから。
これを素朴に tick 空間へ移すと全パラメータが銘柄依存になる。
tick が $0.01 の銘柄で妥当なスプレッドを出す γ が、別の銘柄では5桁になる。

そこで同じ構造を、銘柄が変わっても意味が保たれる単位で表す：

```
skew_ticks  = (inventory_skew_ticks + gamma·σ_ticks) · q_norm
half_spread = base + vol_multiplier·σ_ticks + liquidity_premium/κ
```

`q_norm` は建玉上限に対する比率なので [-1, 1] に収まり、σ は tick 単位なので
両項とも tick。γ・`vol_multiplier`・κ は無次元で、どの銘柄でも同じ意味を持つ。

**手数料はクォート幅に効く。** メイカー手数料 `f` bps を払う以上、
片側あたり最低 `f` bps は稼がねば round trip が成立しない。
`min_edge_bps` がハーフスプレッドの下限として効き、CLI では
`--maker-bps` から自動で設定される。これが無いと、手数料より1桁狭い
スプレッドで喜んで建値を出し、予測精度に関係なく必ず負ける。

### ペーパー約定（`sim/paper.py`）

面白いのはキュー位置。指値は自分の価格で約定が起きたから約定するのではなく、
**先に並んでいた全員を市場が食い破ったから**約定する。
よって各注文は、置いた時点で前方にあったサイズを記憶し、
歩み値がその滞留分を消化してから初めて自分に届く。

モデル化しているもの：

- 板の見えている厚みから決まる FIFO キュー位置
- 価格改善 — スプレッド内側に置けば最前列
- 部分約定と、レベル枯渇のより良い価格への波及
- 発注レイテンシ（決めた瞬間に板に乗るわけではない）

**していないもの**（結果が甘くなる方向）：

- マーケットインパクト
- 自分の前にある見えない板（アイスバーグ等）
- 到着後に追い抜いてくる、より速い参加者
- **ギャップスルー** — 歩み値を挟まず板が指値を飛び越えた場合、
  現実なら通り過ぎざまに誰かに取られているが、ここでは約定しない。
  これがモデル最大の楽観であり、マーケットメイカーが最も恐れる逆選択を
  過小評価する。**P&L は推定値ではなく上限として読むこと。**

`cancel_ahead_ratio` は最大の不確実性に対する唯一の正直なつまみ。
歩み値なしに自分のレベルの厚みが減ったとき、それが自分の前で消えたのか
後ろで消えたのかは観測できない。0.0 は悲観（全部後ろ）、1.0 は楽観（全部前）。

### リスク（`mm/risk.py`）

全クォートサイクルは発注前にリスクゲートを通る。ゲートは
両建て継続 / 片側のみ / 全取消 / 停止 を返す。停止は**ラッチする**。
ドローダウン超過は次のティックで数字が改善しても解除されず、
明示的にリセットするまで固定される。

ステールネス判定は見た目より重要。10秒前に更新が止まった板に建値を出すのは、
下落相場で唯一の買い手になる典型的な経路。

## 合成市場について

`SyntheticFeed` はドリフトなしのランダムウォーク。
**したがってマーケットメイカーは手数料前でほぼフラットになるのが正しい。**
ここで安定して利益が出るなら、それは戦略が良いのではなく
シミュレータが壊れている。

デフォルト値は個別に現実的というより**相互に整合**するよう選んである。
100ms あたり 0.1bps は日次約1%に相当し、8 tick のスプレッドと 2万 lot の
レベルと組み合わせると、内側に置ける程度に広く、キュー位置が意味を持つ程度に
深い板になる。

実際に手数料 1bps を指定すると：

```
$ jsboard backtest --maker-bps 1.0
  fills : 0    total P&L : +0.00 USDT
```

ハーフスプレッド下限が 640 tick（$6.40）まで広がり、
合成市場の $0.08 スプレッドでは一切約定しない。
これはバグではなく正しい結論で、$0.08 のスプレッドに対して
1bps のメイカー手数料を払う BTCUSDT 現物のマーケットメイクは成立しない。

## 現状の制約

- 発注はペーパーのみ。実発注パスは無い
- ギャップスルー約定を模擬していない（上記）
- MM パイプラインは単一銘柄。クロス銘柄のヘッジや相関リスクは扱わない
- Binance のみ。他取引所は `Feed` を実装すれば差し替え可能
- σ は 1 更新あたりの実現ボラで、日中の季節性は持たない
- **`capture` は実データに一度も当てていない**（開発環境から
  binance.com への通信が塞がれているため）。ロジックはフェイクソケットで
  検証済みだが、実際の fapi / fstream での挙動は未確認

## 結論 — 3回とも、手数料で止まった

この調査は終了した。**すべて実データによる測定で、意見ではない。**

| 調べたこと | 結果 |
|---|---|
| マーケットメイク | 実手数料で置ける銘柄 **1件**（手数料0なら10件） |
| 数秒の方向予測 | 10秒の値動き 0.95 bps < 往復コスト 9.03 bps。**算数として不可能** |
| 1時間の方向予測 | 必要 60.8%、実測 **47.6%**。学習では57.8%だった |

3つ目が最も示唆的だった。学習期間で最良だった信号が、検証期間では
コイン投げ以下に落ちた（57.8% → 47.6%）。**時系列分割を守らなければ
「57.8%の的中率」を成果として報告していた。**

詳細と数字は [SPEC.md](SPEC.md) §15。

### 検証していないこと

「エッジは存在しない」の証明ではない。試したのは単一特徴・符号のみの
12信号、14日ぶん、単一製品。組み合わせも機械学習もクロス製品特徴も
未実施。そして閉じたのは**固定ホライズン・全時点・両側テイカー**という設計で
あって、「秒単位に優位性が無い」ではない。必要的中率の式は勝ち幅と負け幅が
等しい前提の簡略形で、利確・損切りを置けば話が変わる。イベント条件付きの
条件付き平均変動も、無条件平均の 0.95 bps より大きくなり得る。

## 使える道具として残るもの

上のスキャン／マーケットメイクが測っているのは「**マーケットメイクの適性**」で、
「**予測できるか**」ではありません。BTC が落ちたのは板が読めなかったからではなく、
最良気配1段でのメイク適性が低いからです。別の問いには別の道具が要ります。

```bash
jsboard horizon --symbol BTCUSDT --days 7    # 値動きが手数料を超えるか
jsboard predict --symbol BTCUSDT --days 14   # 信号が必要精度に届くか
jsboard capture --symbol BTCUSDT             # 現物+先物を1本の時系列に記録
jsboard scan --maker-bps 10                  # 全銘柄のメイク適性
```

`horizon` と `predict` は**別の銘柄・別の手数料でそのまま使える**。
別の市場を検討するときは、作り込む前にこの2つを通すのが安い。
