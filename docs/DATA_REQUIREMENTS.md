# データ取得要件定義書

文書ID: `DAT-001`
対象リポジトリ: `araiy555/bitcoin` / `jsboard`
対象コマンド: `jsboard capture`
版: 1.0

## 0. この文書の範囲

`jsboard capture` が「どの市場から、何を、どの形式で取得し、どこへ保存するか」だけを定義する。
戦略の採否条件は `docs/CROSS_MARKET_REQUIREMENTS.md`、実装の全体像は `SPEC.md` を参照。

---

## 1. 取得対象の市場

1回の `capture` は同一銘柄について次の2市場を**同時に**受信し、**1本の時系列**へ書き出す。

| 呼称 | 市場 | 契約種別 | 例 |
|---|---|---|---|
| `spot` | Binance 現物 | 現物 | BTCUSDT |
| `perp` | Binance USDⓈ-M 先物 | **無期限先物 (Perpetual)** | BTCUSDT Perpetual |

### 1.1 先物の種別（確定事項）

取得しているのは **USDⓈ-M の無期限先物 (USDT建てパーペチュアル)** である。

- 決済通貨: USDT
- 限月: **なし**（無期限）。四半期先物・当限は取得しない
- COIN-M（コイン建て、`dapi`）は**対象外**
- 接続ホストが `fapi.binance.com` / `fstream.binance.com` であることが、USDⓈ-M であることの根拠

選定理由は、現物との数量・決済通貨が揃い、価格発見の主導権が無期限先物側にあるため。
現物と限月先物では受渡日が異なり、ベーシスに金利要因が混ざるため比較単位として使わない。

## 2. 取得するデータ

### 2.1 現物 (`spot`)

| 種別 | 取得元 | 既定間隔 |
|---|---|---|
| 板の差分 | WS `<symbol>@depth@<N>ms` | 100ms（`--spot-depth-ms` で 100 / 1000） |
| 板の初期状態 | REST `GET /api/v3/depth` | 接続時および再同期時 |
| 約定 | WS `<symbol>@aggTrade` | 発生都度 |

接続先:

- WS `wss://stream.binance.com:9443/stream`
- REST `https://api.binance.com`

### 2.2 無期限先物 (`perp`)

| 種別 | 取得元 | 既定間隔 |
|---|---|---|
| 板の差分 | WS `<symbol>@depth@<N>ms` | 100ms（`--perp-depth-ms` で 100 / 250 / 500） |
| 板の初期状態 | REST `GET /fapi/v1/depth` | 接続時および再同期時 |
| 約定 | WS `<symbol>@aggTrade` | 発生都度 |
| マーク価格・Funding率 | WS `<symbol>@markPrice@1s` | 1秒 |
| 強制決済 | WS `<symbol>@forceOrder` | 発生都度 |
| 建玉残高 | REST `GET /fapi/v1/openInterest` | 15秒（`--oi-interval`） |

接続先:

- WS（板） `wss://fstream.binance.com/stream`
- WS（約定・マーク・清算） `wss://fstream.binance.com/market/stream`
- REST `https://fapi.binance.com`

先物のWSは**経路が2系統に分かれている**。板を `/market/stream` へ、約定を `/stream` へ要求すると、
エラーではなく**無言で何も返ってこない**。この分離は実測に基づく確定事項であり、
1本にまとめてはならない。

### 2.3 板の整合（現物・先物共通）

差分と初期状態は次の手順で接合する。手順4・5を省くと、破綻していない見た目のまま
静かに誤った板になる。

1. 差分ストリームを開いて蓄積を開始する
2. RESTで初期状態を取得し `lastUpdateId` を記録する
3. `u <= lastUpdateId` の差分を捨てる
4. 最初に適用する差分は初期状態をまたぐこと (`U <= lastUpdateId+1 <= u`)
5. 以後は `U == 直前のu + 1` を満たすこと。欠落を検知したら再同期する

## 3. 記録形式

1イベント1行のJSON（JSONL）。現物と先物は**同一ファイルに到着順で交互に**書く。
別々に録って後から突き合わせる方式は採らない。取引所時刻の比較可能性に依存してしまい、
到着順そのものが観測対象であるため。

### 3.1 各行に必ず入る項目

| キー | 内容 |
|---|---|
| `src` | `spot` または `perp` |
| `k` | イベント種別 (`delta` / `snapshot` / `trade` / `mark` / `oi` / `liq` / `status`) |
| `schema_version` | 記録形式の版 |
| `capture_id` | 録画1回ごとに一意 |
| `event_seq` | 録画内の通し番号 |
| `venue` / `market_type` | `binance` / `spot`・`perp` |
| `symbol_native` / `instrument_id` | 取引所表記の銘柄 / `BTC/USDT:perp` 形式 |
| `ts_exchange_ns` | 取引所が付けた時刻 |
| `ts_receive_ns` | 受信側の単調時計（市場横断の順序はこれで決める） |
| `ts_wall_ns` | 受信側の壁時計 |
| `connection_id` | 接続単位の識別子 |

取引所時刻と受信時刻の**両方**を残す。前者は市場が何をしたか、後者は戦略が何を知り得たか
を表し、片方だけでは後から問い直せない。

### 3.2 付随ファイル

`<出力名>.meta.json` に、両市場の tick size・lot size・銘柄を記録する。
これが無いと再生時に価格の刻みを推測することになり、推測を誤ると全価格が静かにずれる。

## 4. 保存先

### 4.1 ローカル

`--out` で指定したファイル。S3転送を使う場合は分割ファイル
`<名前>-<開始ns>-<連番>.jsonl` として書かれ、転送成功後に削除される。

### 4.2 S3

| 項目 | 値 |
|---|---|
| バケット | `jsboard-capture`（`--s3-bucket`） |
| リージョン | ap-northeast-1 |
| キー | `raw/symbol=<SYMBOL>/date=<YYYY-MM-DD>/hour=<HH>/<開始ns>-<連番>.jsonl.gz` |
| 圧縮 | gzip（実測 約6倍） |
| 転送単位 | 15分または64MBごと（`--rotate-minutes`） |
| 保持期間 | 7日（ライフサイクルルール `expire-7d`、プレフィックス `raw/`） |

Hive形式のパーティションにしているのは、後から Athena で日・時間・銘柄を指定して
必要な範囲だけ読むため。

### 4.3 認証

boto3 の標準チェーン（環境変数・共有設定・インスタンスロール）からのみ取得する。
**コードに認証情報を渡す引数は存在させない。** 録画に認証情報が混ざれば、それは
バケットに置かれた認証情報になる。

`aws login` による一時認証は数時間で失効するため、長時間の録画には使えない。
失効後の分は転送に失敗し、ローカルに残置される（消えはしない）。

---

## 5. 失敗時の扱い

| 事象 | 動作 |
|---|---|
| S3転送の失敗 | 録画は継続。該当分割ファイルはローカルに残置し、完了時に一覧表示する |
| WS切断 | 再接続し、板は再同期する。切断回数を記録する |
| 先物の約定・マークが無音 | 10秒待ってRESTへ切替（`--perp-fallback auto`） |
| 板の欠番検知 | 再同期。欠落したまま継続はしない |

## 6. 想定データ量（実測値）

BTCUSDT 現物＋無期限先物の同時録画。

| 期間 | イベント数 | gzip後 |
|---|---|---|
| 1時間 | 約166,000 | 約14MB |
| 1日 | 約400万 | 約336MB |
| 1か月 | — | 約10GB |

7日保持の場合、S3の保管料は月額10円程度（無料枠内）。
持ち出し（ダウンロード）は1GBあたり約0.114ドルかかるため、解析はS3側で行うか、
必要な範囲だけ取得する。

## 7. 検証済みの動作

- 60秒の録画がS3へ2分割で転送されること（2026-09-10 確認）
- 1時間のBTCUSDT録画で現物76,335件・先物89,712件を取得（2026-09-10 確認）
- 認証失効時に録画が継続し、データがローカルに残ること（同上）
