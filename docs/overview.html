jsboard — 仕様と測定結果

作ったもの、測ったこと、そして止まった場所

Binance の板を取り込んでマーケットメイクと方向予測を検証するために書いたコードの全体像と、 実データで出た結論。3つの独立した測定が、いずれも同じ場所で止まった。

実装 Python 3.11+ 本体 4,855 行 テスト 3,821 行 / 325 件 実発注 無し

1. これは何か

仮想通貨で自動売買をするために、まずそもそも儲かる余地があるのかを測る道具です。 順番としては、板を読む仕組みを作り、成立しそうな銘柄を探し、値動きと手数料を比べ、 信号が当たるかを検証する、という流れになっています。

結果として売買の仕組みは一通り動きますが、儲かる余地は見つかりませんでした。 その経緯と数字を以下に全部書きます。

すべて jsboard <コマンド> で動きます。通信欄が「なし」のものはオフラインで動きます。

3. 測定 ①　マーケットメイクは成立するか

建値を出して稼げるのは1往復あたり最大でスプレッド1回分、対して手数料は買いと売りの両方にかかります。 つまり スプレッド > 手数料 × 2 でなければ、1回売買するごとに必ず損をします。

1時間（5分間隔×12回）の走査を、手数料10bps と 0bps の2条件で回しました。

手数料 10 bps手数料 0 bps
一度でも手数料を超えた銘柄24 件131 件
75%以上の回で注文が置けた 1 件13 件

拘束条件は板の薄さではなく手数料でした。 手数料をゼロにすると通る銘柄が13倍に増えます。

BTC がここで落ちた理由

BTCUSDT は板が厚く安定していますが、スプレッドが1 tick しかありません。 上限手数料（＝スプレッド÷2、これを下回る手数料が取れれば成立する水準）は 0.00 bps。 板の厚みは 95,041 で、他の銘柄の4〜19倍あります。

これは「BTC は予測できない」という判定ではありません。「BTC ではメイカーとして立てない」という判定です。 行列が9万5千あるところに 0.01 の注文を置いても、順番は回ってきません。

実際、ASTERUSDT で live を走らせたところ、434回の判断サイクルで約定 0 件でした。 自分の注文の前に 75,274 個並んでいて、スプレッドは1 tick。動作は正常で、成果がゼロという状態です。

4. 測定 ②　数秒先の方向は当てられるか

方向を当てる取引は、当たれば値動きぶん儲かり、外せば値動きぶん損して、どちらでも手数料を払います。 必要な的中率は式1本で出ます。 

必要な的中率 = (1 + 往復コスト ÷ 平均の値動き) ÷ 2

モデルは要りません。値動きの大きさと手数料だけで決まります。 そして往復コストが平均の値動きを超えていれば、この数字は100%を超えます。 毎回完璧に当てても手数料で負ける、という意味です。

BTCUSDT 無期限・7日間・全約定

BTC は10秒で平均 0.95 bps しか動きません。往復コストは 9.03 bps。9.5倍の差があります。

これは予測精度の問題ではなく、動く幅より手数料のほうが大きいという算数です。 当初の構想だった「板の歪みを見て1〜10秒の方向を当てて成行で入る」は、ここで閉じました。

ETHUSDT でも同じ形でした。10秒の平均変動 1.51 bps に対し往復コスト約 9.1 bps。 BTC より1.6倍よく動きますが、まだ6.7倍足りません。

5. 測定 ③　1時間先なら信号は届くか

上の表で唯一余地があったのが1時間です。しかも「大きく動く場面だけ」に絞れば、 必要な的中率は 55.4% まで下がります。そこで、実際に届くのかを測りました。

14日ぶんの全約定を、前半8日で12個の信号から1つを選び、後半6日で一度だけ答え合わせしました。 同じデータで選んで測ると、信号の良さではなく「選び方の上手さ」を測ることになるためです。

学習期間検証期間1回あたり損益
mom_900s（逆張り）57.8% 47.56%−11.08 bps
常に買い（基準）— 46.88%−10.59 bps
必要だった的中率—60.8%—

学習期間で最良だった信号が、検証期間ではコイン投げ以下でした。 57.8% → 47.6%。必要だった 60.8% には13ポイント足りません。

これは「調整すれば良くなる」ではなく、信号が実在せず前半の相場にたまたま合っていただけ、という典型的な形です。 同じデータで測っていたら「的中率57.8%の信号を発見」と報告するところでした。

学習期間の順位も、今見ると症状

逆張りが上位を独占し、窓が長いほど成績が良い（900秒 57.8% ＞ 300秒 53.5% ＞ 60秒 50.1%）。 きれいすぎます。前半がレンジ相場だっただけです。 検証期間は「常に買い」の基準が 46.88%、つまり下落局面で、相場つきの変化とともに信号が壊れました。

基準を50%ではなく「常に買い」に置いているのは、上げ相場では何も考えずに買い続けるだけで 的中率が50%を大きく超えるからです。見るべきは水準ではなく、基準との差です。

ここが計画に効きました。板の細かい動き（何段目がいくつキャンセルされたか）は過去データから作れません。 ライブで記録するしかなく、それが capture を作った理由です。清算はライブでも過去でも取れません。

ライブデータで分かった落とし穴

先物のソケットは、購読を受理して「有効」と返答しながら、約定・マーク価格・清算を1件も配信しませんでした。 板だけは正常に届きます。同じ手順を現物に対して行うと全部返ってきます。

それらを配信する別ホストは存在しましたが、テストネットでした。 板の通し番号が本番と10.8兆離れ、価格が現物から55 bps 乖離（本物のベーシスは一桁 bps）。 「データが返ってくるから」で切り替えていたら、下流の分析が全部静かに嘘になっていました。

REST は影響を受けていなかったので、約定とマーク価格はポーリングに落としました。 fromId で前回の続きから引けるため、間引きではなく全件取得できます。 失うのは受信時刻の精度（約1秒）だけで、取引所時刻はそのまま入ります。

8. 実際に注文を出す部分について

この経路は存在しません。意図的に作っていません。

API キーを受け取る箇所も、取引所へ注文を送る関数も、コード上にゼロです。 全コマンドは公開データの読み取りのみです。live は本物の板を読みますが、 約定したかどうかは自分で判定しています。

作るとしたら、必要なのはこれだけあります。

  • 署名付きリクエスト（HMAC-SHA256、timestamp、recvWindow）
  • 発注・取消・照会
  • ユーザーデータストリーム — 自分の約定を取引所から確認する経路。これが無いと注文が通ったか分からない
  • 安全装置 — 二重発注防止、残高確認、建玉上限、緊急停止、通信断からの復帰

作業量は半日〜1日です。

API キーは会話に貼らないでください。 環境変数に置いて、私が一度も見ない形にします。会話に貼られたものは残り、 リポジトリに入れば公開されます。作るときは出金権限をオフ、IP ホワイトリスト、 少額の別サブアカウントから始めるのが安全です。

9. 検証していないこと

ここまでの結論は「エッジが存在しない」の証明ではありません。試していないことを正確に書きます。

  • 試したのは単一特徴・符号だけの12信号。組み合わせも機械学習も未実施
  • 14日ぶんのみ。複数の相場つきをまたいでいない
  • 現物と先物のクロス特徴を使っていない（取得部分はあるが未使用）
  • ペーパー約定はギャップスルーを模擬していないので、損益は上限として読むべき
  • capture の REST 迂回経路は、実装後の長時間記録をまだ取っていない

ただし板の特徴量が効く時間帯（秒単位）は算術的に閉じています。 そこは何を作っても開きません。残っているのは分単位以上の、まったく別のゲームです。

10. 残っている選択肢

1. 手数料の条件を変える

すべての数字がここで決まっています。ただし USDⓈ-M の VIP9（1.7 bps）でも往復 3.4 bps で、 10秒の 0.95 bps には届きません。VIP 昇格では短期テイカーは救えません。 別の取引所か、メイカーリベートのある場所を探すことになります。

2. 保有時間を分〜時間に伸ばす

15分と1時間には余地があります。ただしそれは板を見るゲームではなく、 資金フローや建玉を見る別の戦略になります。今あるコードの大半は使いません。

3. 別の市場で測り直す

horizon は銘柄名を変えるだけで数分で答えを出します。 作り込む前にこれを通すのが安いやり方です。

4. ここで止める

3つの独立した測定が、いずれも同じ壁を指しました。手数料の条件が動かないなら、 これが最も誠実な選択だと考えています。ただし、それはあなたが決めることです。
